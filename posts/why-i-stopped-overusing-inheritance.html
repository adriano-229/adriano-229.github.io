Why I stopped overusing inheritance

For a long time I reached for inheritance by default. A Dog is an Animal, a Car is a Vehicle, and so on. It felt like the "correct" object-oriented way to model the world.

The problem shows up later, once the hierarchy has to represent something the real world doesn't respect: a Penguin that can't fly(), or a Square that breaks Rectangle's contract the moment you try to set width and height independently.

Composition ages better

Composition sidesteps most of this. Instead of asking "what is this thing," you ask "what can this thing do," and you assemble behavior from small, swappable pieces.

class FlightBehavior:
    def move(self):
        return "flying"

class WalkBehavior:
    def move(self):
        return "walking"

class Bird:
    def __init__(self, behavior):
        self.behavior = behavior

    def move(self):
        return self.behavior.move()

No exceptions to carve out, no NotImplementedError stubs, no diamond problem to reason about.

Where inheritance still earns its place

I haven't abandoned inheritance entirely. It's still the right tool when you have a genuinely closed, stable taxonomy — UI widget frameworks, for instance, or exception hierarchies where FileNotFoundError really is an OSError and always will be.

The rule I use now: reach for composition first, and only climb the inheritance ladder when the "is-a" relationship is unlikely to ever be violated by a future requirement.
